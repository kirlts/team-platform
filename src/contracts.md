# Core contracts

What the core (`src/server.js`, `src/worker.js`, `src/db`, `src/queue`, `src/api`, `src/events`, `src/identity`, `src/domain`) expects from the other modules and what it offers to its clients. The numbers and their sources are in `src/config.js` and in `.env.example`.

## 1. Modules the core loads

They are imported by path (`ANALYZE_MODULE`, `EXTRACT_MODULE`, `PROVIDERS_MODULE`). If a file does not exist the server starts anyway and the job that needs it fails with `error_code: module_unavailable`.

| Module | Signature | What the core does with the result |
|---|---|---|
| `src/extract/index.js` | `extract(attachment, { providers, onProgress, signal }) → { text, meta }`. `attachment = { id, input_id, kind, name, mime, size, sha256, path }`; `path` is absolute (for `link`, the URL). `onProgress(percent, phrase)` with `percent` from 0 to 100 for the attachment's step. It does not receive the application configuration. | Stores `text` and `meta` in the attachment row. |
| `src/extract/index.js` | `estimateAudioSeconds(attachment, { signal }) → seconds`, `createAudioBudget() → { check(seconds, at), record(seconds, at) }` | Before extracting audio or video: `check`; with no quota the job is deferred `waitMs` without spending the attempt (`phrase: «Esperando cupo de transcripción»`); with quota, `record`. An infinite `waitMs` fails with `audio_budget_exceeded`. |
| `src/analyze/index.js` | `analyze(bundle, { providers, analyzer, onProgress, signal }) → { status, proposal, units, calls, stats }`. `onProgress({ percent, phrase })`. `bundle = { text, attachments:[{id,kind,name,extracted}], areas:[{id,title,description,position}], templates:[{id,area_id,name,description,body_markdown}], members:[{id,name,profile}], project:{name,description}, recent_inputs:[{id,created_at,text_excerpt,proposed_titles:[string]}] }`, where `recent_inputs` (UD-025) are the same person's other inputs that are `analyzing` or `proposed` and not published, newest first, bounded in count and age (`RECENT_INPUTS_MAX`, `RECENT_INPUTS_MAX_AGE_MINUTES`) and carrying the beginning of the extracted text (`RECENT_INPUTS_EXCERPT_CHARS`): it is context for the model, the core neither compares nor deduplicates; `profile` is the member's complete free text (UD-023, no trimming) and only current areas and templates. | `status: 'ok'`: stores the proposal (`proposal.messages[]` with `area_id` and `template_id` per message, `discarded`) and `units`. `refusal`, `max_tokens` or `invalid`: the input fails without retry, with `error_code` equal to the status. A proposal with `area_id` and `template_id` at the root is normalised to one per message. |
| `src/analyze/index.js` | `warmTemplate({ providers, config, templateMarkdown })`, `resolveConfig()` | The core calls it when a template is saved (event `template.saved`), with no clock-based waits. |
| `src/analyze/seed.js` | `loadSeed(dir) → { areas, templates }` | Installation seed (`templates/areas.json` and the files it lists). |
| `src/analyze/templates.js`, `errors.js` | `parseTemplate(markdown)`, `compileFieldsSchema(fields, { validation: true })` | A single definition of a valid template: the core uses it when saving a template (422 if it does not comply) and when validating the `fields` of each message on publish. |
| `src/analyze/templates.js`, `validate.js` | `compileOutputSchema(markdownOrTemplate, { validation = false }) → schema \| null`, `validateOutput(output, markdownOrTemplate) → { errors }` | The output a worked message must deliver (UD-254 (5), H-3723). `markdownOrTemplate` is the template file, the result of `parseTemplate` or its `output` list. `null` when the frontmatter has no `output` block. The schema is `{ type: 'object', properties, required, additionalProperties: false }` with the declared entries in their order, then `outcome` (`done`, `investigated`, `blocked`, `needs_decision`) and `summary` (text for the person who sent the message, UD-255 (5)); both are always required and a template cannot declare them. Entry types: `text` → string (with `enum` if declared), `list` → array of strings, `number`, `boolean`. `validation: false` is the grammar for `claude -p --json-schema` (no `minLength`; optional means an optional property; more than 24 optional entries are refused when the template is saved). `validation: true` is what `validateOutput` checks: a required text and `summary` cannot be empty, an optional entry admits absence or `null`. `errors` is empty when the output is valid, `['the template declares no output']` without a block. Only the frontmatter counts: a `## Salida` section of the body is prose that travels with the body and is never compiled. |
| `src/providers/index.js` | `createProviders(env) → { text, vision, speech, textFallback, describe() }` | Built from the environment plus what is stored in Settings (`TEXT_*`, `VISION_*`, `SPEECH_*`) and rebuilt when that changes. `describe()` feeds `GET /settings/providers` and `GET /health`. A key is never exposed. |
| `src/execute/deliver.js` | `createDeliverHandler(...)`, `outputJson(output) → string`, `heldBody({ output, template, reason, language }) → string`, `DELIVER_LATER = 75`, `DELIVER_HELD = 76` | The `deliver` job (UD-263, UD-266). The command of `EXECUTE_DELIVER_COMMAND` receives `TEAM_OUTPUT_JSON` (compact JSON of the structured output without `summary`). Exit 0 delivered, 75 later, 76 held for a person (last stdout line = reason; no retry; job `done`, `delivered = 0`, `execute_runs.delivery_held = 1`; one reply with `outcome: needs_decision`), other = failed. The platform knows no zones. |

**Errors and retries.** An error with `retryable === false` fails the job immediately. The core assigns it to `ExtractError`s except `link_timeout` and `link_fetch_failed`, and to analyzer and provider errors with `code` in `input`, `template`, `harness_unavailable`, `config`, `refusal`, `max_tokens`, `invalid_output`, `unsupported`. The rest are retried with exponential backoff and jitter up to `QUEUE_MAX_ATTEMPTS`. The model calls that a job managed to make stay traced even if the job fails. The error's `code` reaches the client in `error_code` (`GET /inputs/:id` and the `done` event).

**Model calls.** Each provider opens its own span with the `gen_ai.*` attributes (UD-014); the core stores nothing separately. `llm_calls` is a view over `spans` (`0002_telemetry.sql`, a copy of `src/telemetry/migration.sql`).

## 2. Telemetry (UD-014)

`src/telemetry/` is used as it is (`src/domain/tracing.js` re-exports what the worker and the API use). `initTelemetry({ db, serviceVersion })` runs after migrating and before the API and the worker, in the server and in the separate worker; `shutdown()` flushes the batches on shutdown. Each attempt of a queue job is the root of its own tree: `withSpan('job', { 'team.job_id', 'team.input_id', 'team.step': 'job', 'team.job_kind', 'team.attempt' })` with the result in `team.outcome` (`done`, `requeued`, `failed`, `deferred`, `released`, `lost`) and `error.type` if it failed. Publishing, closing and reopening open `input.publish`, `message.close` and `message.reopen`. `GET /api/jobs/:id/trace` (editor) returns `traceOfJob` after flushing the export queue; 404 if the job left no spans. Span retention (`pruneSpans`) goes with that of jobs and events (`RETENTION_DAYS`).

The database connection keeps `synchronous=FULL` and SQLite's WAL autocheckpoint (1,000 pages). The telemetry report measured that each automatic checkpoint pauses the loop for about 30 ms and that `wal_autocheckpoint=0` with a checkpoint of our own brings it down to 1.4 ms (`src/telemetry/README.md`); it is not adopted because 30 ms every ~4 MB of WAL is not on the critical path of an input (the steps last seconds) and a checkpoint of our own adds a timer that, if it fails, lets the WAL grow without bound.

## 3. What the core offers

**Process.** Reads `DATA_DIR` (default `/data`), `DB_PATH` (default `$DATA_DIR/team.db`), `HOST` and `PORT`. Attachments in `$DATA_DIR/attachments`, a copy of the edited templates in `$DATA_DIR/templates`. `GET /health` answers 200 only with the database migrated and 503 otherwise. SIGTERM: stops claiming, closes the SSE streams, aborts the jobs in progress and returns them to the queue with the attempt refunded, closes the API and the database (measured under 1 s, Docker deadline 10 s). JSON logs to stdout (pino); each worker line carries `job_id` and `input_id`.

**API.** Everything under `/api` (plus `/health` at the root). The OpenAPI 3.1 contract comes from the route schemas: `GET /api/openapi.json`. Conventions:

- Every id travels as text in responses, SSE included. Inputs accept text or integer; an invalid id is 400.
- Every POST and PATCH with a body rejects unknown properties. 401 without a session, 403 without a role, 409 for uniqueness (member email, current area title, template name within an area).
- Every list is `{ items, page, limit, total }`, with `?page=&limit=` and a cap of 100. Areas and the templates of an area are bounded lists and return an array.
- Every destructive operation requires `?confirm=true`. Areas and templates are soft-deleted (`deleted_at`) and restored with `POST /areas/:id/restore` and `POST /templates/:id/restore`; the messages that reference them are not lost.
- Error bodies: `{ code, message, ...extra }`, messages in Spanish.
- Messages come out flat (`area_id`, `author_id`, `assignee_ids`, `reply_count`, `last_reply`); names are resolved with `GET /members` and `GET /areas`. A member carries `profile` (free text, UD-023). `GET /me` carries `project_name`. `GET /inputs/:id` carries `units: [{ id, text }]` and the proposal with text ids. Each input of `GET /inputs` also carries `percent`, `phrase` and `proposed_count`; `GET /inputs?mine=1&status=queued,extracting,analyzing,proposed` is the panel's inbox of inputs (UD-025), in creation order.
- Publishing (`POST /inputs/:id/publish`) accepts the proposal exactly as `GET /inputs/:id` delivers it (`messages`, `discarded`, `unit_ids`). A null `template_id` uses the first current template of the message's area.
- An unsafe request with the session cookie requires `X-Team-Request` (the panel sends `panel`).
- The accepted image attachments are raster (png, jpeg, webp, gif, heic, heif, avif). A HEIC/HEIF photo (iPhone) is decoded to JPEG with ffmpeg before the vision provider (UD-040); one that cannot be read fails at extraction with `image_heic_unreadable`, one over 50 megapixels with `image_too_many_pixels`. SVG is rejected with 415 because it can carry scripts.

**Events.** `GET /api/events`, one stream per member. Events `progress` (`job_id`, `input_id`, `percent`, `phrase`, `at`), `done` (`job_id`, `input_id`, `done: true`, plus `status`, `error`, `error_code`) and `message` (`message_id`, `title`, `author_id`, `at`, one per published message). `id` is `job_events.seq`; `Last-Event-ID` replays without duplicates or gaps. `?job_id=` narrows to one job and answers 204 if it already finished and there is nothing to replay.

**Cross-origin.** `CORS_ORIGINS` (list of origins; empty = same origin, no CORS) with `credentials: true`. `COOKIE_MODE=cross-origin` sets `SameSite=None; Secure` and the CSRF hook accepts only a listed `Origin`. With `same-origin` (the default) the cookie is `__Host-` with `SameSite=Lax`.

**Editor operations.** `GET /jobs?state=` and `DELETE /jobs?state=&confirm=true` (finished only), `POST /inputs/:id/reprocess` (also a published input, UD-258: its messages go to the trash), `GET /audit`, `GET /health` with database, queue and provider detail, `GET /jobs/:id/trace`.

**Execute (UD-254, UD-255, H-3724).** An agent member is created with `POST /members { email, name, role?, profile?, kind: 'agent' }` (Editor); the 201 response carries `agent_secret` once and never again, and a `password` is 400 `agent_has_no_password`. The agent authenticates with `X-Team-User`, `X-Team-Ts` (Unix seconds) and `X-Team-Sig` = HMAC-SHA256(secret, `ts.METHOD.path.email`) under any `IDENTITY_PROVIDER`; `request.member.source` is `agent`. A job `{ kind: 'execute', message_id, payload_json: { message_id, member_id, requested_by } }` is enqueued when a published message is assigned to an active agent (on publish and on edit) and by `POST /messages/:id/execute { member_id? }` (Editor; 202 `{ job_ids }`; 409 `no_agent_assignee`, `execute_busy`, `message_closed`, `not_an_agent`). `POST /jobs/:id/progress { percent, phrase }` is for the job's agent only (403 `not_job_agent`, 409 `job_not_running`). The session's `--json-schema` is `compileOutputSchema(template)` with `summary` required (only `summary` when the template declares no output); a valid `structured_output` becomes the agent's closing reply, anything else fails the job (`invalid_output`, `execute_error`, `execute_no_result`, `execute_timeout`, `host_instructions_missing`). `scripts/team.mjs` (`show`, `reply`, `progress`, `close`) reads `TEAM_URL`, `TEAM_AGENT_EMAIL`, `TEAM_AGENT_SECRET`, and optionally `TEAM_API_PREFIX` and `TEAM_JOB_ID`; it uses only Node built-ins so it can be copied into a machine. Progress events of an `execute` carry `message_id` and go to the whole team; its `done` carries `message_id`, `reply_id`, `session_id`, `cost_usd`. The `execute` span carries `team.session_id` and `team.cost_usd`.

**Development.** `POST /api/auth/dev-login` exists only with `NODE_ENV=development`.

## 3 bis. Client package

`packages/client` (`@team-platform/client`) is the client of this contract: `openapi.json` is `GET /api/openapi.json` of the test server, `src/generated/schema.ts` its types and `src/generated/error-codes.ts` the request error codes found in `src/`. `npm run gen:client` rewrites the three; `src/client-contract.test.js` fails when the server and the files differ. A new route needs its entry in `packages/client/src/routes.ts` (or in `NOT_IN_CLIENT`, with the reason).

## 4. Tests

`npm test` runs everything with `node --test` on an ephemeral SQLite database. `node src/testing/smoke-panel.mjs` starts the server with the compiled panel and walks the main flow in a windowless browser.
